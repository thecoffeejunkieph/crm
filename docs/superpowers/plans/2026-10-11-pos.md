# Retail POS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `/pos` page where a cashier rings up a walk-in sale. The sale is stored as a `PAID` invoice with `channel=POS`, stock is deducted at once, and the customer gets a printed and/or emailed receipt.

**Architecture:** The backend adds a `channel` column to `invoice` and a new `PosSaleService` that prices the sale on the server, validates split payments, persists the invoice and its payments, and calls the new `InventoryService.sellForPos`, all in one transaction. A thin `PosController` sends the receipt email after commit. The frontend adds a `src/components/pos/` folder and `pages/Pos.tsx`, with cart state in `useReducer`, and renders the receipt from the server response.

**Tech Stack:** Spring Boot, JPA/Hibernate (`ddl-auto=validate`), Flyway on MySQL, JUnit 5 + Mockito, Thymeleaf PDF. React 19, TypeScript, Tailwind, @tanstack/react-query, axios, react-hot-toast.

**Spec:** `docs/superpowers/specs/2026-10-11-pos-design.md`

## Review Focus

1. **Double-tapped Confirm, or a retry after a network drop.** Only one sale and one stock deduction should happen. `/api/v1/pos/sales` must be in `IdempotencyFilter.PATHS`, and the UI must reuse the same key on retry. *(Test: Task 5, `IdempotencyFilterPathsTest`.)*
2. **Another register sold the last unit while this cart was open.** The checkout returns 409 naming the product, and nothing is saved. That includes no invoice and no payments. The service must not swallow the exception. *(Test: Task 3, `stockFailurePropagates`.)*
3. **A product that was never received** (no `InventoryItem` row). The grid shows "0 left" and the sale fails with `InsufficientStockException`, not a 404. *(Tests: Task 2, `sellWithoutInventoryRecordIsInsufficientStock`; Task 4, `searchDefaultsMissingInventoryToZero`.)*
4. **"Email receipt" ticked for a customer with no email.** The sale succeeds with `emailStatus=NOT_REQUESTED`, not `FAILED`, and no mail is attempted. *(Test: Task 5, `noCustomerEmailIsNotRequested`.)*
5. **Exactly-half centavo amounts.** For example, a 50% discount on ₱10.05 must give ₱5.03 (HALF_UP), not ₱5.02 (HALF_EVEN). Server and on-screen preview must agree. *(Tests: Task 3, `roundsHalfUp`; Task 8, the matching case in the self-check.)*

### Task 8: Pricing preview and API client

**Files:**
- Create: `components/pos/posTotals.ts`, `components/pos/posTotals.check.ts`, `components/pos/posApi.ts`

**Interfaces:**
- Produces:
  - In `posTotals.ts`:
    - `type DiscountType = "PERCENT" | "FIXED"`
    - `type CartLine = { product: PosProduct; quantity: number; unitPrice: number; discount: number | null; discountType: DiscountType | null }`
    - `applyDiscount(gross: number, discount: number | null, type: DiscountType | null): number`. It rounds half-up to centavos via `Math.round((x + Number.EPSILON) * 100) / 100`, and clamps invalid discounts to the bounds.
    - `lineTotal(line: CartLine): number`
    - `cartTotals(lines: CartLine[], discount: number | null, type: DiscountType | null): { subtotal: number; discountAmount: number; total: number }`
  - In `posApi.ts`:
    - Types `PosProduct` (mirrors `PosProductResponse`), `PosSaleRequest`, `PosPayment = { method: PaymentMethod; amount: number; amountTendered?: number }`, `PosSaleResponse = { invoice: PosInvoice; change: number; emailStatus: "NOT_REQUESTED" | "SENT" | "FAILED" }`, and `PosInvoice`, which holds the `InvoiceResponse` fields the receipt uses (including `channel`, `listPrice` and `amountTendered`)
    - `usePosProducts(q: string, categoryId: number | null, page: number)`, a `useQuery` keyed `["pos-products", q, categoryId, page]`
    - `useCheckout()`, a `useMutation` that takes `{ request: PosSaleRequest; idempotencyKey: string }` and sends the `Idempotency-Key` header
    - `useEmailReceipt()`, a `useMutation` that takes `(invoiceId: number)`

### Task 10: Payment, success view and printed receipt

**Files:**
- Create: `components/pos/PaymentModal.tsx`, `components/pos/PosReceipt.tsx`
- Modify: `pages/Pos.tsx`, `index.css` (print rules)

**Interfaces:**
- Consumes: `useCheckout`, `useEmailReceipt` and `cartTotals` (Task 8); `PAYMENT_METHOD_OPTIONS` and `paymentMethodLabels` from `utils/paymentMethod`.
- Produces:
  - `PaymentModal` props: `{ isOpen, total: number, customerHasEmail: boolean, onClose, onConfirm(payments: PosPayment[], emailReceipt: boolean) }`
  - `PosReceipt` props: `{ sale: PosSaleResponse }`. It renders inside `<div id="pos-receipt">`.

- [ ] **Step 1: Implement**

Follow the spec sections "Checkout flow" and "Receipt":
- Opening the modal creates `crypto.randomUUID()` in a ref. Every retry reuses it, and it is cleared on success or close.
- "Remaining" is total − Σ amount, and Confirm is enabled only when it is exactly 0.00 (compare in centavos).
- Tendered is shown only for CASH, and change per row is tendered − amount.
- On a 409 response, toast the message, refetch `["pos-products"]`, and flag the lines whose quantity exceeds the refreshed `quantityAvailable`.
- The success view shows invoice number, total and change. Its actions are **Print receipt** (`window.print()`), **Email receipt** (`useEmailReceipt`) and **New sale** (`clear`). For `emailStatus === "FAILED"`, show a toast with a Resend action.
- The receipt and the success view read only from `PosSaleResponse`. The receipt's per-payment change is `amountTendered − amount`. Show "was ₱X" when `listPrice !== price`.

Print CSS in `index.css`:

```css
#pos-receipt { display: none; }
@media print {
  body * { visibility: hidden; }
  #pos-receipt, #pos-receipt * { visibility: visible; }
  #pos-receipt { display: block; position: absolute; inset: 0 auto auto 0; width: 100%; max-width: 80mm; }
}
```
