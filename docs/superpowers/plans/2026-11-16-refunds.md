# Refunds Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Approved, partial, money-only or goods-return refunds on paid orders, paid out with a recorded method, documented by a credit memo, and netted out of stock, insights and reports.

**Architecture:** A new `Refund` aggregate in the `sales` module (entity + lines, `RefundService`, `RefundController`), approval via the existing `Approvals` + `ApprovalDecided` listener pattern (mirrors `inventory/AdjustmentService` / `AdjustmentApprovalListener`). Stock goes back through a new public `Inventory.receiveReturn`. Insights and reports switch from the `payment` table to a `money_movement` view that adds paid refunds as negative rows.

**Tech Stack:** Spring Boot, JPA, Flyway (Postgres), JdbcTemplate SQL, existing PDF/Tailwind template pipeline; React + Vite + generated OpenAPI client, vitest.

**Spec:** `docs/superpowers/specs/2026-11-16-refunds-design.md`

## Review Focus

1. **Two refunds racing on one order** (two tabs) — the second must see the first under the order lock and fail the refundable/returnable guard, not over-refund. → Task 2 test `concurrentRequestsCannotExceedRefundable` (sequential second request after first commits is enough; the lock is the mechanism).
2. **Approval granted after the order changed** (another refund paid meanwhile) — payout must re-check guards and fail with a clear error, leaving the refund APPROVED. → Task 3 test `payoutRechecksGuards`.
3. **Order line shipped from two warehouses** — the return must go to the warehouse the user picked, and the per-warehouse returnable qty must not exceed what that warehouse shipped. → Task 3 test `returnGoesToChosenWarehouse`.
4. **Money-only refund on a CANCELLED order with collected money** — allowed; goods return on it rejected. → Task 2 test `cancelledOrderAllowsMoneyOnlyOnly`.
5. **Rejected or cancelled refunds** must free their amount/qty for a new request. → Task 2 test `rejectedRefundFreesAmount`.

- Produces:

  - `RefundService.request(Scope, long orderId, RefundRequest) → RefundResponse`, `list(Scope, long orderId) → List<RefundResponse>`, `cancel(Scope, long refundId, long version) → RefundResponse`, package-private `decided(long refundId, boolean approved)`, `static final String ENTITY = "REFUND"`.
  - Endpoints: `GET /api/orders/{id}/refunds` (`canRead`), `POST /api/orders/{id}/refunds` (`canWrite`), `POST /api/refunds/{id}/cancel` body `TransitionRequest` (`canWrite`).
  - `record Returnable(long orderLineId, long warehouseId, BigDecimal shipped, BigDecimal returned)` and `RefundService.returnable(long orderId) → List<Returnable>` — shipped = `sum(delivery_order_line.picked_qty)` of dispatched delivery orders (`dispatched_at is not null`) grouped by `order_line_id, warehouse_id`; returned = sum of non-REJECTED/CANCELLED `refund_line.qty` for the same key. Exposed on `GET /api/orders/{id}/refunds/returnable` (`canRead`) for the dialog.

Rules (spec §2 guards): line amount = `qty × coalesce(netTotal, lineTotal) / line.qty`, HALF_UP 2dp; refundable = `settledAmount − refundedAmount − sum(amount of REQUESTED/APPROVED)`; `GOODS_RETURN` needs status `RELEASED`/`FULFILLED`; order must have `settledAmount > 0`. Admin → status `APPROVED` + `Approvals.ensureApproved` audit path (call it; it records `SELF_APPROVED` for admins); non-admin → `REQUESTED` + `requestOnBehalf(new CreateApprovalRequest(REFUND, ENTITY, refund.id, 0, Map.of("amount", amount, "orderNumber", o.number), reason), userId)`. `RefundApprovalListener` mirrors `AdjustmentApprovalListener` (AFTER_COMMIT, REQUIRES_NEW, only `ENTITY` subject, idempotent on REQUESTED).
